# 首次 Vibe Coding 复盘（先规划再动手）

> 本次项目：CHO小站 个人博客（Vite + React + 无后端 Markdown 方案 + GitHub Pages 部署）
> 记录人：自己 | 时间：2026-10-21

## 一、需求与技术方案层面

**问题 1：技术方向反复横跳，做了无用功**
- 过程：先做纯前端 → 想加后端记录访问数 → 想写「作者编译器」→ 最终回到「纯静态、无后端」。
- 结果：写了 `后端.md` 又作废删除，中间几次方案设计都白费了。
- 改进：**动手前先把根本性决策想清楚并写进方案文档**，尤其是「要不要后端」这种影响全局的问题。方案定了再写代码，比边做边改省得多。

**问题 2：需求细节没提前说清**
- 过程：AI 批量生成文件时，把「占位文章」写满了内容，被拒后才知道占位文章应该留空。
- 改进：占位数据、示例内容的用途要一开始就说清楚（「占位 = 空」「示例 = 要有具体内容」），别让 AI 猜。

## 二、对项目架构 / 数据模型的理解

**问题 3：没理解「一篇文章 = 一个 .md 文件」**
- 过程：把几篇文章的内容都写进同一个 `hello.md`，以为归档和最新日志会各自分开展示。
- 改进：先搞懂内容系统的数据模型——**文件就是文章，一个文件一篇**；`index.json` 是清单，决定「显示哪些、按什么顺序」。

**问题 4：写文章没同步更新 index.json**
- 过程：新增/修改文章后，网页不更新，因为清单没跟着改。
- 改进：记住「加一篇 = 两步」：① 建 .md 文件 ② 把文件名加进 `index.json`。缺一不可。

## 三、对构建 / 部署的理解

**问题 5：改错了文件——改了构建产物**
- 过程：去改 `dist/index.html`，结果 git 不追踪、每次 build 又被覆盖。
- 改进：分清**源文件**和**构建产物**。`dist/` 是 `npm run build` 生成的，永远别手动改；要改就改源文件（根目录 `index.html`）。

**问题 6：对 GitHub Pages 部署机制不熟**
- 过程：部署时连续踩坑——不知道子路径（base）、不知道 SPA 刷新会 404、不知道 Pages 要手动开启、不知道私有仓库免费账号开不了 Pages。
- 改进：部署前先让 AI 把托管平台的机制讲清楚（地址结构、路由、开启步骤、限制），再照着做，不要边试边撞。

## 四、调试 / 排查能力

**问题 7：遇到「不显示」没有第一时间看 Console**
- 过程：文章列表空白，反复确认数据、代码、部署，绕了一大圈，最后靠 F12 Console 的一句 `Buffer is not defined` 才定位到根因。
- 改进：**前端出问题，先按 F12 → Console 看红色报错**。报错信息往往已经点明原因，比从数据层一步步猜快得多。

**问题 8：对「本地 dev」和「线上」两个环境理解不足**
- 过程：改了 `base` 后本地地址从 `localhost:5173/` 变成 `localhost:5173/CHO_own_web/`，没意识到；线上还有缓存、部署延迟等问题。
- 改进：理解 dev 和 build/线上是两个不同环境，**路径、缓存、生效时机都不一样**。排查时先明确「我现在看的是哪个环境」。

## 五、对所用技术的预期

**问题 9：拿「通用 Markdown 编辑器」的预期套「网页渲染器」**
- 过程：测试了数学公式、脚注、高亮、emoji、原生 HTML 等，结果大多不渲染，以为坏了。
- 改进：用新工具前先了解它的**能力边界**。本项目用的是 react-markdown + remark-gfm，只支持标准 Markdown + GFM 扩展，数学公式/脚注/高亮等需要额外插件。

## 六、Vibe Coding 方法本身

**问题 10：过度依赖 AI，关键机制没主动搞懂**
- 过程：数据流（文件 → index.json → fetch → 解析 → 渲染）、构建、部署这些关键环节，都是 AI 在搭，自己没吃透，导致反复踩同样的坑。
- 改进：**AI 给的方案，关键环节要自己理解「为什么这么做」，而不是只看结果**。遇到报错，先自己读一遍报错信息，试着判断一下原因，再决定要不要求助。

## 总结

这次最大的收获不是做出了博客，而是暴露了几个通用短板：**方案不先定、模型不先懂、报错不先看、环境分不清**。下次动手前，先把「技术方案 + 数据模型 + 部署方式」三件事问清楚、写下来，开发过程中遇到问题先看报错，能少走一大半弯路。
